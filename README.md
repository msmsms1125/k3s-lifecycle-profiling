# K3s Lifecycle & TinyLlama Workload Profiling

Raspberry Pi 기반 ARM64 클러스터에서 **K3s의 주요 동작에 걸리는 시간과 시스템 자원 사용량**을 측정한 프로젝트입니다.

클러스터 시작, 애플리케이션 배포, 스케일링, 재시작 등의 동작을 반복 실행하고, TinyLlama 추론 워크로드까지 실험 범위를 확장했습니다.

이후 기존 로그와 측정 코드를 검토하면서 처리시간 계산과 부하 생성 방식의 문제를 찾아 수정했습니다.

## 1. 프로젝트 목표
- **처리시간:** 클러스터 시작·배포·스케일링·재시작에 각각 얼마나 걸리는가?
- **반복 실행의 차이:** 같은 동작을 반복했을 때 처리시간은 얼마나 달라지는가?
- **자원 사용:** 유휴 상태와 애플리케이션·LLM 실행 상태에서 자원 사용 패턴은 어떻게 달라지는가?

## 2. 실험 환경

실험 목적에 따라 두 가지 클러스터 구성을 사용했습니다.

| 구분 | 클러스터 구성 | 실험 내용 |
|---|---|---|
| Phase A | Master 1대 + Worker 1대 | K3s 시작 및 Nginx 배포·스케일링·재시작 등 |
| Phase B | Master 1대 + Worker 3대 | TinyLlama 배포·스케일링·추론 부하 등 |

| 항목 | 환경 |
|---|---|
| 하드웨어 아키텍처 | ARM64 / aarch64 |
| 컨테이너 오케스트레이션 | K3s `v1.34.3+k3s1` |
| 자원 모니터링 | Netdata, 5초 단위 평균 데이터 |
| 이벤트 시간 기록 | Unix timestamp, 초 단위 |
| 실험 시나리오 | 총 17개 |

장비 사양과 설치 과정은 [환경 구성 문서](docs/setup)에 정리했습니다.

## 3. 주요 결과

### 이벤트 로그로 처리시간 재계산

보존된 이벤트 로그 60개에서 **7개 시간 지표, 총 70개 관측값**을 다시 계산했습니다.

각 지표는 10회 실행 결과를 바탕으로 평균·중앙값·최솟값~최댓값을 정리했습니다.

![이벤트 로그로 다시 계산한 처리시간](docs/assets/lifecycle-event-timings.png)

| 환경 | 측정한 동작 | 반복 횟수 | 평균 | 중앙값 | 최솟값~최댓값 |
|---|---|---:|---:|---:|---:|
| A | K3s Master 시작 → Ready | 10 | 13.7초 | 12.0초 | 12~23초 |
| A | Nginx 배포 요청 → 배포 완료 | 10 | 6.8초 | 3.5초 | 3~19초 |
| A | Nginx 축소 후 확장 | 10 | 5.3초 | 4.0초 | 4~9초 |
| A | Nginx 롤아웃 재시작 | 10 | 9.1초 | 9.0초 | 6~12초 |
| B | TinyLlama 복제본 1 → 3개, Ready까지 | 10 | 43.6초 | 40.0초 | 38~52초 |
| B | TinyLlama 복제본 3 → 1개, 완료까지 | 10 | 23.6초 | 23.5초 | 21~27초 |
| B | TinyLlama 롤아웃 재시작 → Ready | 10 | 37.8초 | 35.5초 | 35~48초 |

### 결과에서 확인한 점

- **평균과 중앙값을 함께 볼 필요가 있었습니다.**  
  Nginx 배포시간은 평균 6.8초, 중앙값 3.5초이며, 관측 범위는 3~19초였습니다. 평균만으로는 반복 실행 사이의 차이를 충분히 보여주기 어려웠습니다.

- **TinyLlama 확장 시 준비 완료까지의 대기시간을 확인했습니다.**  
  복제본을 1개에서 3개로 늘리는 데 평균 43.6초가 걸렸으며, 실행별 범위는 38~52초였습니다.

> 위 수치는 해당 실험 환경에서 초 단위로 기록한 관측값입니다.
> Phase A와 B는 장비 구성과 워크로드가 다르므로 직접적인 성능 비교에 사용하지 않습니다.

## 4. 측정 과정에서 발견하고 수정한 문제

| 문제 | 결과에 미치는 영향 | 수정 내용 |
|---|---|---|
| 이벤트 처리시간에 안정화 대기시간이 포함됨 | 실제 동작에 걸린 시간이 과대 계산될 수 있음 | 이벤트 완료 시점과 안정화 구간을 분리 |
| 한 요청의 응답을 기다린 뒤 다음 요청을 전송함 | 응답이 느려질수록 실제 요청률이 낮아짐 | 응답 완료와 독립적으로 예정 시각에 요청을 보내도록 코드 수정 |
| 시간 순서·중복·지표 범위 등의 데이터 문제 | 통계와 누적 자원 사용량 계산이 잘못될 수 있음 | 타임스탬프 정렬·중복 제거, 지표 열 식별 및 범위 검사 추가 |

수정한 부하 생성 코드는 모의 SSE 서버를 이용해 실제 클러스터 없이 동작을 검증했습니다. 문서·의존성·익명화 상태 등의 검사도 CI에 포함했습니다.

**수정 코드를 기존 하드웨어에서 다시 실행하지는 못했으므로, 코드 수정 후의 실제 클러스터 성능 결과는 제시하지 않습니다.**

## 5. 결과를 해석할 때의 범위

현재 자료는 다음과 같이 구분합니다.

| 자료 | 활용 범위 |
|---|---|
| 위 표의 7개 처리시간 지표 | 보존된 이벤트 로그에서 재계산 가능 |
| 과거 CPU·메모리·디스크 등 자원 측정 결과 | 자원 변화 경향을 살펴보는 참고 자료 |
| Step 17의 기존 추론 부하 결과 | 목표한 1 RPS가 유지되었음을 입증하지 못해 검증 대상에서 제외 |

### 주요 한계

- 기존 ARM64 클러스터를 더 이상 사용할 수 없어 하드웨어 재실험을 수행하지 못했습니다.
- 5초 단위 평균 자원 데이터로는 짧은 이벤트의 순간 최대 사용량을 정밀하게 측정하기 어렵습니다.
- 원시 Netdata CSV와 Step 17 요청 원본이 보존되지 않아 관련 과거 파생 통계를 재계산할 수 없습니다.
- 결과는 하나의 실험 환경에서 얻은 관측값이며, K3s의 일반적인 성능을 나타내지는 않습니다.

자세한 기준은 [결과 유효성 문서](docs/RESULT_VALIDITY.md)와 [수치별 근거 문서](docs/EVIDENCE_MAP.md)를 참고하세요.

## 6. 실행 및 검증

Python 가상환경을 만들고 분석 의존성을 설치합니다.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

실제 클러스터 없이 수행할 수 있는 검사는 다음 명령으로 실행합니다.

```bash
python tools/run_offline_checks.py
```

이 검사는 로그 기반 집계와 저장소 검사, 오프라인 테스트를 수행합니다. 실제 Raspberry Pi 클러스터에서 실험을 다시 실행하는 명령은 아닙니다.

상세 실행 조건은 [재현성 가이드](docs/REPRODUCIBILITY.md)에 정리했습니다.
